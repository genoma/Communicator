# File & Image Attachments

Supported formats, interactive and one-shot usage, gating, and limits. See the [README](../README.md#documentation) for the full docs index.

Attach local files to a message so the model can see or read them. Queued files are sent with the next message, and the original message text goes along unchanged. Attachments persist in the session file (as OpenAI-style content parts), so `--resume` replays them and re-sending works.

Supported formats:

| Kind     | Extensions                                              | How it is sent                                        |
|----------|---------------------------------------------------------|-------------------------------------------------------|
| Image    | `png`, `jpg`, `jpeg`, `gif`, `webp`, `bmp`, `avif`, `tif`, `tiff`, `heic`, `heif` | base64 `image_url` part — requires a vision model; `avif`/`tif`/`tiff`/`heic`/`heif` are converted to `jpeg`/`png` first (`heic`/`heif`: macOS only) |
| PDF      | `pdf`                                                   | base64 `file` part (server-side parsing; only on models that support file input) |
| Office   | `xlsx`, `xls`, `docx`, `pptx`                           | base64 `file` part — **Venice only** (server-side extraction) |
| Text     | `txt`, `md`, `markdown`, `csv`, `json`, `yaml`, `yml`, `toml`, `xml`, `log`, `py`, `js`, `mjs`, `cjs`, `ts`, `tsx`, `jsx`, `css`, `html`, `sh`, `sql`, `go`, `rs`, `java`, `c`, `cpp`, `h`, `hpp`, `ini` | inlined as a `text` part (no base64 bloat) |

Anything else is rejected with `Unsupported file type: <ext>`.

- **Interactive** — `/attach <path>...` queues one or more files (relative paths resolve from the current directory). Each file prints `attached: <name> (<kind>, <size>)` or an error line, and one failing file does not abort the rest. Paths with spaces can be backslash-escaped (`/attach Screenshot\ 2026-07-23.png`).
- **Clipboard** — `/paste` queues an image straight from the system clipboard, no path needed: macOS prefers a file URL when the pasteboard carries one (a Finder copy or a staged screenshot — the file is read exactly like `/attach <path>` and named from its basename), and otherwise reads the pasteboard's PNG flavour through `osascript` (with a TIFF fallback); Windows through PowerShell 5.1's `Get-Clipboard -Format Image`, Linux through `wl-paste` or `xclip`. The label is the clipboard file's basename when there is one — control and bidi/zero-width characters plus characters illegal in filenames removed, whitespace collapsed, leading dots stripped, capped at 80 characters keeping the extension — and `clipboard-<hh-mm-ss>.png` otherwise; both print the same `attached:` line, and a clipboard without an image prints `No image in the clipboard.`. The label is display-only: replay and `--export` name image attachments from the wire mime (`image.png`), never from this label. The file-URL route does no content sniffing: a URL pointing at a missing, unreadable or non-image file falls into the same no-image line, and a file over the 20 MB limit prints `The clipboard image is larger than 20 MB.` when no image flavour is readable. macOS TIFF fallback bytes go through the normal conversion path, so a machine without the optional image codec reports the conversion failure instead — and a pasteboard offering only a huge screenshot's raw TIFF flavour (tens of MB) can hit the 20 MB raw limit even though its PNG flavour would not.
  - `/attach` with no arguments lists the queue, `/attachments` lists it too, and `/attachments clear` empties it. Queued files are sent with the very next message you type and the queue resets; `/new` also clears the queue.
  - Words without a file extension or path separator are treated as prose and ignored with a hint.
  - Type your message on the next line, not after the paths — a multi-line submission uses the first line as the command and sends the remaining lines as your message.
- **One-shot** — `--attach <path>` is repeatable and requires a prompt argument or piped stdin (`communicator --attach report.pdf "Summarize"`). It cannot be combined with `--resume`, `--export`, `--delete`, `--list-*`, or bare `--config`.
- **Vision gating** — image attachments are blocked at attach time when the selected model is known to lack vision (`The selected model does not support image input.`). Unknown capability allows the attachment — API errors surface naturally. On models known to lack vision, `/attach`, `/paste` and `/attachments` are hidden from the session-start hint, the autocomplete, and the unknown-command list, though typing them manually still works (text/PDF attach stays available); `/model` to a vision model re-shows them in the autocomplete and unknown-command list (the banner hint stays as it was when the session started). Text files work on any model; PDFs (and office files on Venice) need a model that supports file input — on OpenRouter the model's `supported_parameters` must include `file` (models without a parameter list stay assumed-capable), and the gate rejects with `The selected model does not support file attachments.` otherwise. Office files are rejected on OpenRouter with a clear message (`xlsx/docx/pptx are only supported on Venice...`) and accepted on Venice.ai, which extracts them server-side.
- **Switching models** — `/model` re-checks the queue against the new model and drops entries it can't accept, with a warning line per dropped file.
- **Image preprocessing** — before sending, png/jpg/jpeg/webp attachments are downscaled to a 2048 px long edge and re-encoded with EXIF (including GPS) stripped, when the prebuilt image codec is available; EXIF orientation is baked in first. `avif`, `tif`/`tiff` and `heic`/`heif` are always converted, because providers do not reliably accept the originals: the target is `png` when the decoded image has transparency, otherwise `jpeg` (quality 90) — the macOS HEIC decode yields an opaque `jpeg`, so `heic`/`heif` always land on `jpeg` — and a must-convert format has no passthrough: when the conversion cannot be done (no image codec, a failed HEIC decode, an undecodable, multi-page or oversized-pixel image), the attach fails with `Cannot read attachment: <path> (image conversion failed)`. gif, bmp, animated WebP and PNG, images over the 50 MP decode cap, undecodable png/jpg/jpeg/webp images and runs without the codec pass through byte-for-byte. `heic`/`heif` decode through the macOS system converter (`sips`) only: on Linux and Windows they are rejected before the file is read with `Unsupported file type: heic (HEIC/HEIF images are supported on macOS only — convert to JPEG or PNG)` (the `heif` spelling for a `.heif` file). The `attached:` size, the bytes stored in the session and `--export` are the transformed ones — a converted attachment replays and exports as `image.jpeg`/`image.png`, since only the converted bytes are persisted.
- **Limits** — images over 20 MB and pdf/office files over 25 MB are rejected based on the raw file size; text files over 25 MB are rejected too. The data URL sent on the wire is up to a third larger than that raw size (base64 inflation), which is not what these limits measure. Inline text over 256 KB is still accepted but warns about context usage.
- **Display & export** — resumed sessions render `attached: <filename> (<kind>)` lines under user messages (replay prints `(file)` for pdf/office where live `/attach` prints `(pdf)`/`(office)`) and `image: <filename>` / `file: <filename>` lines under assistant messages (images show as `image.<ext>` because only the image URL is persisted; pdf/office keep their real filenames); `--export` materializes image/pdf/office attachments as real files under `session-<id>/attachments/` and renders `> **Attachment:** [<filename>](attachments/<filename>)` links for user attachments (the label keeps the attachment's original name while the file on disk uses the sanitized one) (assistant-produced parts render `> **Image:**` / `> **File:**`); text-file attachments stay inline in the message text with no filename line; `/copy` copies only the message text, never file contents or base64.
